How it would work

The thesis stands: the model never edits the document. It proposes, in the vocabulary the sidebar already has, and every change goes through your hands. What changes in v2 is who runs the model and what the copy edit is checking against.

1 · TriggerPick pass, model, effort, scope. A revision is saved first. A run row is created and a background job starts.
2 · PromptThe numbered rulebook, the pass’s baseline instructions, house rules, and the document with numbered paragraphs.
3 · Codexcodex exec under your ChatGPT login, read-only sandbox, ephemeral, with a strict JSON output schema.
4 · AnchorEach finding names a paragraph, an exact quote, and a rule. The open editor places the highlight; misses become orphaned cards, nothing lost.
5 · ActCards appear as windows return. Accept, edit, dismiss, or bulk-apply. Counts per rule update.

Using your ChatGPT subscription

Your machine already has Codex CLI 0.154.0 signed in with ChatGPT. The app treats it as the model runner rather than talking to OpenAI itself. Each run is one subprocess per document window:

codex exec --ephemeral --skip-git-repo-check -s read-only \
  -m gpt-6-astra -c model_reasoning_effort=medium \
  --output-schema findings.schema.json -o findings.json \
  "<prompt: rules, pass instructions, house rules>"   < document.txt

The document is piped on stdin (Codex wraps it as a <stdin> block), the schema forces a valid JSON reply, and --ephemeral keeps the run out of Codex’s session history. Sign-in state is codex login status; signing in from the app runs codex login --device-auth and shows the code it prints. Model and effort are per-run flags, so a cheap fast model for proofreading and a strong one for line edits is a per-pass setting.

  • Why this and not our own OAuth: OpenAI’s ChatGPT sign-in is only supported through Codex. Reimplementing its token flow means an undocumented endpoint and a client id that isn’t ours; it works until it doesn’t. Driving the CLI stays inside the supported surface and inherits fixes when you run codex update.
  • Trade-offs: Codex must be installed and signed in (it is). Usage counts against your plan’s limits; the run strip shows a clear message if a window is rate-limited, and the run resumes when you retry. Each window is a fresh session, which is what we want: no memory between runs.
  • Provider interface stays: CodexProvider now; an API-key provider, Anthropic, or a local model is one class each, later, if ever.

The rulebook

A rule is a row: number, one line of text, optional tag, enabled flag, sort order, and counters for fired and dismissed. The number is stable for the rule’s life, so cards and the editor’s letter can say “R7” and mean the same thing next month. Editing is inline HTMX: click to edit, Enter to save, drag to reorder, checkbox to disable without deleting. Import and export are plain text, one rule per line, so the rulebook can live in a note or a repo as well.

At run time the enabled rules are rendered into the prompt as a numbered list, and the schema’s rule field ties each finding back to one of them (or null for a general finding, which the pass can forbid). House rules that ride along with every pass: preserve the author’s voice; quote the smallest span; one change per card; never rewrite a whole paragraph unless the pass says so; if unsure whether something is deliberate, ask. The reply schema:

{
  "summary": "Rules checked, which fired and how often, anything global",
  "findings": [
    {
      "paragraph": 4,
      "quote": "illuminated",
      "rule": 3,                    // rule number, or null for a general finding
      "kind": "suggest",            // one of the pass's allowed kinds
      "replacement": "lit",         // required for suggest, null otherwise
      "comment": "Rule 3: prefer the plain word.",
      "confidence": "high"
    }
  ]
}

Long documents are split into ~1,500-word windows by paragraph, each its own Codex call with the full rulebook, so findings stream in and no window is too big to check carefully. Continuity-type rules (R14) get the whole document when it fits the budget.

Anchoring findings to text

Unchanged from v1. Models are bad at offsets and good at quoting, so each finding names a paragraph number and an exact quote. Placement happens in the live editor: exact match in the hinted paragraph, then exact unique match anywhere, then a normalised match (curly vs straight quotes, dashes, whitespace), then a fuzzy window match above a high threshold. Misses are kept as orphaned cards with quote, rule, and comment visible. Placing on the client means a pass can run while you keep typing, and a document opened later still receives its pending cards.
